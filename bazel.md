# Building with Bazel

This repository can be built with [Bazel](https://bazel.build) in addition to
the existing `go build` and `envsetup.sh` workflow. The Bazel setup uses
[rules_go](https://github.com/bazel-contrib/rules_go) and
[Gazelle](https://github.com/bazel-contrib/bazel-gazelle), and it wires the Elm
frontend and the protobuf code generation into a single dependency graph.

The Bazel build is an alternative, not a replacement. The `siot_*` shell
functions and plain `go build` continue to work.

## Why Bazel here

`go build` already resolves Go imports, caches compiled packages, and builds
incrementally, so for pure Go code Bazel adds little. The value in this project
comes from the steps that surround the Go build:

- **One graph across languages.** The frontend is Elm, the wire format is
  protobuf, and both feed the Go binary through `go:embed` and generated code.
  With Bazel, editing an Elm source or a `.proto` file invalidates exactly the
  downstream targets that depend on it, including the final binary. Plain
  `go build` cannot see across those boundaries; it embeds and compiles whatever
  bytes happen to be on disk.
- **Reproducibility for codegen.** The protobuf bindings are generated during
  the build from a Bazel-built `protoc`, so they cannot drift from the `.proto`
  sources.
- **A foundation for shared caching.** Once the graph is correct, a remote cache
  or remote execution can be added so CI and the team reuse build and test
  results.

If the project were Go only, the shell scripts would be the simpler choice.

## Prerequisites

- **Bazel 9.x.** The version is pinned in `.bazelversion`. Using
  [Bazelisk](https://github.com/bazelbuild/bazelisk) is the simplest way to get
  the matching version automatically.
- **A JDK** for the Bazel server. Bazel needs `javac`, not just a JRE. On a host
  where `javac` is not on `PATH`, point the server at a JDK in an untracked
  `user.bazelrc` (see
  [Machine-specific configuration](#machine-specific-configuration)).
- **Node, npm, and the Elm toolchain** for the frontend build. These run on the
  host; see [Frontend (Elm)](#frontend-elm) for details and the rationale.
- A C/C++ toolchain, used transitively to build `protoc`. Most developer
  machines already have one.

The Go SDK and `protoc` are downloaded and built by Bazel; they do not need to
be installed separately.

## Common commands

```bash
# Build the main binary
bazel build //cmd/siot:siot

# Build everything
bazel build //...

# Run all tests
bazel test //...

# Run the binary
bazel run //cmd/siot:siot -- <args>

# Regenerate BUILD.bazel files after adding, moving, or re-importing Go packages
bazel run //:gazelle

# Sync MODULE.bazel's use_repo list after changing go.mod dependencies
bazel mod tidy
```

The compiled binary is placed at `bazel-bin/cmd/siot/siot_/siot`.

## How it is organized

### Dependencies

`MODULE.bazel` declares rules_go, Gazelle, and protobuf, and pulls Go
dependencies directly from `go.mod` via `go_deps.from_file`. This keeps `go.mod`
and `go.sum` as the single source of truth for versions. The `use_repo` block at
the bottom of `MODULE.bazel` lists the external repositories the build
references; `bazel mod tidy` keeps it in sync.

### Per-package BUILD files

Gazelle generates one `BUILD.bazel` per Go package (a package maps to a
directory in Go). These files are committed. After changing imports or adding
packages, run `bazel run //:gazelle` to regenerate them. The root `BUILD.bazel`
holds the Gazelle configuration directives.

### Protobuf

The protobuf bindings are generated during the build:

- `internal/pb/BUILD.bazel` contains `proto_library`, `go_proto_library`, and a
  `go_library`, generated by Gazelle. The directives that enable this live at
  the top of that file (`proto default` and
  `proto_strip_import_prefix /internal/pb`, the latter so that `node.proto`'s
  `import "point.proto"` resolves within the package).
- The `.proto` files declare
  `option go_package = "github.com/simpleiot/simpleiot/internal/pb;pb"`, a full
  import path so the generated library's import path matches the rest of the
  codebase.
- This path is fully hermetic: Bazel builds `protoc` and the Go plugin itself,
  so no host `protoc` is required for the Bazel build.

The out-of-band `siot_protobuf` workflow in `envsetup.sh` still works and writes
the checked-in `.pb.go` files to `internal/pb/`. The `siot_protobuf_go` function
was updated to pass `--go_opt=module=github.com/simpleiot/simpleiot` so the
output location is unchanged after the `go_package` update.

### Frontend (Elm)

The Elm single-page application is built by a genrule:

- `//frontend:elm_js_gz` (in `frontend/BUILD.bazel`) runs
  `bazel/build_frontend.sh`, which copies the Elm sources into a clean working
  directory and runs `npm ci`, `elm-tooling install`, `elm-spa build`, and
  `gzip`. It produces `frontend/public/dist/elm.js.gz`.
- The frontend `go_library` embeds that generated file through the existing
  `//go:embed public/*` directive in `frontend/embed.go`. The embed entry
  carries a `# keep` comment so Gazelle preserves it even though the file is not
  present in the source tree.
- The Elm sources are declared inputs of the genrule, so editing any file under
  `frontend/src/` rebuilds `elm.js.gz` and relinks the binary.

## Tradeoffs

### The frontend build is not hermetic

`//frontend:elm_js_gz` shells out to the host's node, npm, and Elm toolchain. It
runs with `local = True` and is tagged `requires-network` because `npm ci` may
fetch packages. `.bazelrc` passes `HOME` and `PATH` through to the action so the
`~/.npm` and `~/.elm` caches and the host binaries resolve.

The consequence: a developer building the frontend through Bazel needs node and
npm available, the same as the existing `siot_build_frontend` workflow. Results
are not portable across machines with different toolchain versions in the way a
fully hermetic build would be.

A fully hermetic frontend build is possible by adopting `rules_js` (or
`aspect_rules_js`) and pinning the npm dependency tree and the Elm compiler
through Bazel. That is a larger undertaking and was left out of scope. The
current approach delivers the dependency correctness (Elm sources flow to the
binary) without it. The protobuf path, by contrast, is fully hermetic.

### The generated `elm.js.gz` is no longer committed

Bazel does not allow a genrule output to share a path with a checked-in source
file, so `frontend/public/dist/elm.js.gz` was removed from version control and
the directory is now in `.gitignore`.

The consequence: a plain `go build` on a fresh checkout requires building the
frontend first (`siot_build_frontend`), because `go:embed` needs the file to
exist. The documented build workflow already runs the frontend build before the
backend, so the normal path is unaffected. Anyone relying on `go build`
succeeding without a prior frontend build will need to run it once.

If keeping the committed artifact is preferred, the alternative is to not have
Bazel own that embed. The cost is that the Elm build can no longer be wired into
the Bazel graph.

### Two ways to generate protobuf

The Bazel build generates the bindings from `.proto` at build time, while the
checked-in `.pb.go` files serve the plain `go build` path. Both are kept
consistent through the shared `go_package` setting. Regenerate the committed
files with `siot_protobuf` when the `.proto` files change, as before.

## Machine-specific configuration

`.bazelrc` ends with `try-import %workspace%/user.bazelrc`. Create an untracked
`user.bazelrc` for settings that are specific to your machine. For example, to
point the Bazel server at a JDK when `javac` is not on `PATH`:

```
startup --server_javabase=/usr/lib/jvm/java-21-openjdk
```

`user.bazelrc` is listed in `.gitignore`.

## Files added or changed for Bazel

- `MODULE.bazel`, `.bazelrc`, `.bazelversion`: Bazel module, configuration, and
  version pin.
- `BUILD.bazel` files throughout the tree: generated by Gazelle, plus the root
  file's configuration directives.
- `bazel/build_frontend.sh` and `bazel/BUILD.bazel`: the Elm build wrapper.
- `internal/pb/*.proto`: `go_package` updated to a full import path.
- `envsetup.sh`: `siot_protobuf_go` updated to match the `go_package` change.
- `.gitignore`: ignores Bazel symlink trees, `MODULE.bazel.lock`,
  `user.bazelrc`, and `frontend/public/dist/`.
- `frontend/public/dist/elm.js.gz`: removed from version control (now
  generated).
