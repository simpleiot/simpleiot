# Plan: MQTT — Built-in Server, Subscription Client, and Sparkplug B

**Branch:** `cbrake/master` **Branched from:** `9032d3c3`

## Context

[docs/user/plc.md](../docs/user/plc.md) describes the planned MQTT support:
Simple IoT serves MQTT itself through the embedded NATS server, a subscription
node maps topics into points, and Sparkplug B builds the node structure
automatically from birth certificates. None of it is implemented yet. This plan
covers four phases: exposing the built-in broker, a plain-MQTT client with JSON
payload mapping, Sparkplug B with its topic schema and automatic node creation,
and topic-schema auto-creation for plain MQTT. Schema-less discovery and
connecting to external brokers are noted as follow-on work.

The pieces already in place make this smaller than it looks:

- The embedded NATS server (`server/nats-server.go`) is v2.14.4 with JetStream
  enabled, which is everything the NATS MQTT implementation needs, including QoS
  2 (added in NATS 2.11). Enabling MQTT is filling in `opts.MQTT` and setting a
  server name.
- Messages published over MQTT surface as NATS subjects, so the subscription
  client can consume them over the existing NATS connection — no MQTT client
  library is required until external-broker support is added.
- Protobuf generation is already part of the build (`internal/pb`,
  `siot_protobuf` in `envsetup.sh`), so the Sparkplug B payload definition slots
  into the existing toolchain.

## Design Decisions

**The broker is the NATS MQTT server, configured like the other NATS ports.**
`SIOT_NATS_MQTT_PORT` enables it; unset or `0` keeps it off, matching the
documented plan in plc.md. No CLI flag is added, consistent with the other NATS
port options which are env-only (`server/args.go`).

**A server name is set whenever MQTT is enabled.** NATS requires an explicit
`ServerName` for MQTT because sessions and retained messages live in JetStream
streams tied to that name. The name must be stable across restarts or clients
lose their sessions, so use the instance root node ID (already stable and
unique), falling back to `Options.ID` handling that exists today.

**Auth and TLS reuse what the NATS listener already has.** When
`SIOT_AUTH_TOKEN` is set, the MQTT listener requires it (`opts.MQTT.Token`; an
MQTT client presents it in the CONNECT password field). When
`SIOT_NATS_TLS_CERT`/`KEY` are set, the same certificate serves the MQTT
listener. No separate MQTT credential story in this phase.

**The subscription client consumes NATS subjects, not an MQTT connection.** With
a blank `uri` on the `mqtt` node (the only mode in this plan), the client
subscribes over the existing NATS connection to the converted subject. Topic
levels convert `/` → `.` and a literal `.` → `//`; MQTT wildcards `+`/`#`
convert to `*`/`>`. This keeps the binary free of an MQTT client library.
External brokers (non-blank `uri`) will need one (likely
`eclipse/paho.mqtt.golang`) and are deferred.

**JSON payload extraction is a small dot-path evaluator, no new dependency.**
`path` supports `$.a.b[0]` style access implemented directly over
`encoding/json` (bounded, ~60 lines), the same reasoning that kept the
Prometheus text parser dependency-free. A blank path means the whole payload: a
bare number becomes a `value` point, a bare string a text point, and an object
becomes one point per top-level field with the field name as the point key (the
"node per device" shape from plc.md).

**Sparkplug B payloads decode with generated protobuf code.** Vendor the Eclipse
Tahu `sparkplug_b.proto` into `internal/pb` and generate with the existing
`siot_protobuf` flow. Runtime dependency is `google.golang.org/protobuf`,
already in go.mod.

**Sparkplug topic schema maps directly onto the node graph.** Topic namespace
`spBv1.0/{group}/{message_type}/{edge_node}/{device}`:

- group → `sparkplugGroup` node (child of the `mqtt` node)
- edge node → `sparkplugNode` node (child of the group)
- device → `sparkplugDevice` node (child of the edge node)
- metric → point on the edge-node or device node: type `value` (or text for
  strings), key = metric name passed through `data.SubjectSafeToken` (metric
  names like `Node Control/Rebirth` carry characters the store rejects)

Nodes are created automatically from NBIRTH/DBIRTH — this is the intended
behavior per plc.md, because birth certificates enumerate every metric with name
and type, so there is no guessing. Nodes for edges/devices that publish
NDEATH/DDEATH (or stop publishing) are marked offline via the existing
`sysState` convention rather than deleted.

**Alias cache and rebirth.** After birth, DDATA/NDATA reference metrics by
numeric alias. The client keeps a per-edge-node alias → name map built from the
birth message. On an alias with no mapping (Simple IoT restarted after the
birth), it publishes an NCMD `Node Control/Rebirth` back through the broker —
possible over NATS since subject-published messages reach MQTT subscribers.
Acting as a Sparkplug primary host (the STATE topic) is deferred.

**A topic schema on the `mqtt` node auto-creates nodes for plain MQTT.** plc.md
rejects blind wildcard discovery as the default because nothing in plain MQTT
says which topic level is a device and which is a measurement. A `topicSchema`
point supplies exactly that missing information: `{site}/{device}` declares that
the first level is a site and the second a device, so auto-creation becomes
deterministic rather than guesswork. Named levels become nodes (intermediate
levels reuse `group`, the last named level is a new `mqttDevice` type), each
carrying a tag point named by its schema label and an identity point holding the
raw topic level. Everything beyond the named levels — remaining topic levels
plus JSON field names — joins into the point key via `data.SubjectSafeToken`.
Nodes are matched on the identity point (the same rule that keeps Sparkplug
rebirth from duplicating nodes), created on first message, and never
auto-deleted. A `maxNodes` limit guards against unbounded topic levels, and the
fixed depth of the named part means a rogue deep topic extends a point key,
never the node tree. Topics matched by an explicit `mqttSub` child are skipped
by the schema handler, so precise mappings override the schema.

**New node types** (constants in `data/schema.go`, wired in
`frontend/src/Api/Node.elm` and `frontend/src/Components/`):

| Type              | Purpose                                                          |
| ----------------- | ---------------------------------------------------------------- |
| `mqtt`            | Connection/config node; blank `uri` = built-in broker            |
| `mqttSub`         | Manual topic → point mapping (topic, path, units, scale, offset) |
| `mqttDevice`      | Auto-created from a topic schema; holds the extracted points     |
| `sparkplugGroup`  | Auto-created from topic namespace                                |
| `sparkplugNode`   | Auto-created edge node, holds alias cache metadata               |
| `sparkplugDevice` | Auto-created device                                              |

## Phase 1 — Built-in MQTT server

1. `server/args.go`: parse `SIOT_NATS_MQTT_PORT` (default 0 = disabled) into a
   new `Options.NatsMQTTPort`; thread through `server/server.go` into
   `natsServerOptions`.
2. `server/nats-server.go`: when the port is non-zero, set `opts.MQTT.Port`,
   `opts.MQTT.Token` (from auth token), `opts.MQTT.TLSConfig`/`AuthTimeout` when
   TLS is configured, and `opts.ServerName`. Log the listener the same way the
   WS port is logged.
3. Verify the `$MQTT_*` JetStream streams NATS creates for sessions/retained
   messages do not confuse anything that enumerates streams (store, sync,
   `siot store` tooling per ADR-7); filter by the `si` prefix conventions if
   needed.
4. Tests: broker suite per the Test Plan below, including the shared
   `internal/mqtttest` helper it introduces.
5. Docs: `docs/user/configuration.md` env var list; update the "planned" markers
   in `docs/user/plc.md` for the broker section. Changelog entry.

## Phase 2 — MQTT subscription client (JSON payloads)

1. `data/schema.go`: add `NodeTypeMqtt`, `NodeTypeMqttSub` and point type
   constants (`topic`, `path`).
2. `client/mqtt.go` + `client/mqtt-sub.go`: manager-run client following the
   Modbus/Shelly parent-child pattern (`Mqtt` struct with `child:"mqttSub"`).
   Blank `uri` subscribes over NATS to converted subjects; non-blank `uri` sets
   an error point ("external brokers not yet supported").
3. Topic→subject conversion helpers plus the dot-path JSON extractor, each with
   table-driven tests.
4. Point publishing: scale/offset for numeric values, text points for strings,
   point key from the JSON field name when mapping whole objects. Store the full
   topic as a `tag:topic` point on the `mqttSub` node per the graphing section
   of plc.md.
5. Register in `client/client.go` `DefaultClients`.
6. Frontend: `NodeMqtt.elm`, `NodeMqttSub.elm`, node type registration in
   `Api/Node.elm`, add-node menu entries.
7. Tests: subscription suite per the Test Plan below.
8. Docs: `docs/user/mqtt.md` exists as a planned page (linked from SUMMARY and
   plc.md); flip the subscriptions section from planned to available and
   reconcile it with what shipped. Update plc.md markers. Changelog entry.

## Phase 3 — Sparkplug B (topic schema + automatic nodes)

1. Vendor `sparkplug_b.proto` (Eclipse Tahu, EPL-2.0 — note license in the file
   header) into `internal/pb`; generate via `siot_protobuf`.
2. `data/schema.go`: `NodeTypeSparkplugGroup`, `NodeTypeSparkplugNode`,
   `NodeTypeSparkplugDevice`.
3. `client/sparkplug.go`: a boolean `sparkplug` point on the `mqtt` node (see
   the example below) enables a subscription to `spBv1//0.>`; parse the topic
   into group/type/edge/device; decode the payload.
4. Message handling:
   - NBIRTH/DBIRTH: create/refresh group, edge, and device nodes; build alias
     cache; write one point per metric (initial values). Map Sparkplug types per
     the plc.md data-type table (BOOL→int, numeric→float/int, String→text).
   - NDATA/DDATA: resolve aliases, publish changed metrics as points with the
     payload timestamp.
   - NDEATH/DDEATH: mark the node offline (`sysState`), keep the node.
   - Unknown alias: publish NCMD `Node Control/Rebirth`, drop the sample, log
     once per edge node.
5. Frontend: views for the three node types (description + online state; the
   default point display covers metrics initially).
6. Tests: Sparkplug suite per the Test Plan below.
7. Docs: Sparkplug section of `docs/user/mqtt.md`; flip plc.md markers.
   Changelog entry.

## Phase 4 — Topic-schema auto-creation (plain MQTT)

1. `data/schema.go`: `NodeTypeMqttDevice`; point types `topicSchema` and
   `maxNodes` (default 1000) on the `mqtt` node.
2. Schema parser: fixed prefix levels plus `{name}` levels; derive the
   subscription (`+` per named level, `#` for the remainder, converted to
   `*`/`>`); reject schemas with a `{name}` after a `#`-style remainder.
   Table-driven tests.
3. Message handling: split the topic; named levels resolve to the node path —
   `group` nodes for intermediate levels, `mqttDevice` for the last — creating
   nodes as needed with a tag point per schema label and an identity point
   holding the raw level value. Remaining levels and JSON field names join into
   the point key via `data.SubjectSafeToken`; scalar payloads and
   `$.value`-style objects produce a single point.
4. Node matching on the identity point, so restarts and renames do not
   duplicate; user-set points (tags, description) survive. On reaching
   `maxNodes`, set an error point on the `mqtt` node and drop new topics.
5. Precedence: a topic matched by an explicit `mqttSub` child is not handled by
   the schema.
6. Frontend: schema and max-nodes fields on `NodeMqtt.elm`; `NodeMqttDevice.elm`
   (description, online state, default point display).
7. Tests: schema suite per the Test Plan below.
8. Docs: flip the topic-schema section of `docs/user/mqtt.md` from planned to
   available and reconcile it with what shipped; update the discovery discussion
   in plc.md to describe the schema approach. Changelog entry.

## Example: 15 sites publishing plain JSON to the central broker

A deployment this plan must serve well: 15 sites, each with one or more gateways
(Kepware, Ignition Edge, groov RIO), all publishing plain-JSON MQTT to the
built-in broker on a central instance. This example exercises the Phase 1 and
Phase 2 features together and belongs in `docs/user/mqtt.md` when Phase 2 lands.

### Topic convention

Identity lives in the topic, configured on the gateway side:

```
{site}/{gateway}/{machine}/{measurement}     scalar payloads:  {"value": 42.1}
{site}/{gateway}/{machine}                   device payloads:  {"tank_level": 42.1, "pump_rpm": 1730, ...}
```

### Tree shape

One group node per site carrying a `site` tag, one `mqtt` node per gateway
beneath it (blank `uri` = built-in broker), one `mqttSub` per topic. Tag
inheritance means `site` is set once per site and `gateway` once per gateway;
`machine` sits on the `mqttSub` node. One provisioning file per site in
`<SIOT_DATA>/provisioning/`, each applying idempotently, generated from a
template since only descriptions, tags, and topics vary.

`provisioning/site-plant-07.yaml` — a gateway publishing one scalar per topic
(node per measurement):

```yaml
apiVersion: 1
nodes:
  - group:
      description: Plant 07
      tag:
        site: plant-07
      children:
        - mqtt:
            description: Kepware line 3
            uri: "" # blank = built-in MQTT server
            tag:
              gateway: kepware-l3
            children:
              - mqttSub:
                  description: Tank level
                  topic: plant-07/kepware-l3/press/tank_level
                  path: $.value
                  units: cm
                  tag:
                    machine: press-3
              - mqttSub:
                  description: Oven temp
                  topic: plant-07/kepware-l3/oven/temp
                  path: $.value
                  scale: 0.1 # gateway publishes tenths of a degree
                  units: C
                  tag:
                    machine: oven-1
```

`provisioning/site-plant-12.yaml` — two gateways, one publishing multi-field
device JSON (blank `path`: one point per field, field name as point key):

```yaml
apiVersion: 1
nodes:
  - group:
      description: Plant 12
      tag:
        site: plant-12
      children:
        - mqtt:
            description: Ignition Edge
            uri: ""
            tag:
              gateway: ignition-edge
            children:
              - mqttSub:
                  description: Press 1
                  topic: plant-12/ignition/press1
                  tag:
                    machine: press-1
              - mqttSub:
                  description: Press 2
                  topic: plant-12/ignition/press2
                  tag:
                    machine: press-2
        - mqtt:
            description: groov RIO dock
            uri: ""
            tag:
              gateway: groov-rio-dock
            children:
              - mqttSub:
                  description: Dock door state
                  topic: plant-12/groov-dock/door/state
                  path: $.value
                  tag:
                    machine: dock-door
```

With `tag` listed in the Database node's Tag Point Types, every point arrives
labeled:

```
points_value{key="tank_level",
             "node.tag.site"="plant-12",
             "node.tag.gateway"="ignition-edge",
             "node.tag.machine"="press-1"}
```

What this example implies for the implementation:

- Multiple `mqtt` nodes with blank `uri` against the same built-in broker must
  coexist; each is just a set of NATS subscriptions.
- `mqttSub` nodes carry `tag` points like any other node, so no new tag
  machinery is needed — inheritance and the Database client cover it.
- A wildcard topic on one `mqttSub` would land every match on one node and
  collapse per-machine tags, which is why the docs steer users to named topics
  (and why discovery, when it comes, creates a node per topic).
- Gateways authenticate with the auth token in the CONNECT password field over
  TLS; QoS 1 is the recommended default for telemetry.

### A site publishing Sparkplug B

A site running Ignition Edge with Cirrus Link MQTT Transmission, publishing
Sparkplug B to the same central broker. The configuration is one node, because
the structure below it comes from the birth certificates rather than from the
file:

`provisioning/site-plant-03.yaml`:

```yaml
apiVersion: 1
nodes:
  - group:
      description: Plant 03
      tag:
        site: plant-03
      children:
        - mqtt:
            description: Plant 03 Sparkplug
            uri: "" # blank = built-in MQTT server
            sparkplug: true
```

Transmission is configured with Sparkplug group `plant-03` and edge node
`ignition-edge`. When it connects and publishes
`spBv1.0/plant-03/NBIRTH/ignition-edge` followed by DBIRTH messages, the client
builds:

```
Plant 03 (group, tag: site=plant-03)
└── Plant 03 Sparkplug (mqtt)
    └── plant-03 (sparkplugGroup)
        └── ignition-edge (sparkplugNode)
            ├── press-1 (sparkplugDevice)
            │     points: tank_level, pump_rpm, ...  (one per DBIRTH metric)
            └── press-2 (sparkplugDevice)
```

DDATA updates then resolve aliases against the cache from the birth messages and
land as point updates on the device nodes. A device that publishes DDEATH (or an
edge node that drops and triggers its NDEATH) is marked offline, not deleted.

With `tag` in the Database node's Tag Point Types, the same site label applies
through inheritance, and the Sparkplug structure is queryable without any
per-metric configuration:

```
points_value{key="tank_level",
             "node.type"="sparkplugDevice",
             "node.description"="press-1",
             "node.tag.site"="plant-03"}
```

What this example implies for the implementation:

- Auto-created nodes must be stable across birth messages: an NBIRTH after a
  gateway restart refreshes the existing group/edge/device nodes rather than
  creating duplicates (match on Sparkplug identity, not description).
- The Sparkplug group name and topic identity should also land as tag points
  (`tag:sparkplugGroup`, or similar) on the auto-created nodes, so queries can
  select on them the same way the plain-MQTT example selects on hand-set tags.
- Tags a user adds to auto-created nodes (a `machine` tag on a
  `sparkplugDevice`) must survive rebirth refreshes — birth handling updates
  metric points, never user-set points.
- Mixed sites work: plain `mqttSub` sites and Sparkplug sites differ only in
  their provisioning file, and both shapes end up queryable through the same tag
  scheme.

### The same 15 sites with a topic schema (Phase 4)

When the gateways follow the topic convention, the per-site provisioning files
collapse to one node:

```yaml
apiVersion: 1
nodes:
  - mqtt:
      description: Plant data
      uri: "" # blank = built-in MQTT server
      topicSchema: "{site}/{gateway}/{device}"
```

The first message on `plant-07/kepware-l3/press/tank_level` carrying
`{"value": 42.1}` creates:

```
Plant data (mqtt)
└── plant-07 (group, tag: site=plant-07)          auto-created
    └── kepware-l3 (group, tag: gateway=kepware-l3)
        └── press (mqttDevice, tag: device=press)
              point: value, key tank_level
```

and yields the same labels as the hand-provisioned version:

```
points_value{key="tank_level",
             "node.tag.site"="plant-07",
             "node.tag.gateway"="kepware-l3",
             "node.tag.device"="press"}
```

The trade against the per-site files is metadata: hand-provisioned `mqttSub`
nodes carry units, scale, and curated machine tags, while schema-created nodes
know only what the topic says. The two compose — start with the schema to see
what 15 sites are publishing, then add explicit `mqttSub` entries (which take
precedence) for the values that need units, scaling, or careful naming.

## Deferred (documented as still planned in plc.md)

- External brokers (`uri` set) via an MQTT client library.
- Per-client MQTT credentials. Design sketch: an `mqttUser` node type (user,
  bcrypt password hash, optional `topicPrefix`) watched into an in-memory cache,
  wired into the embedded server through `opts.CustomClientAuthentication`. The
  authorizer accepts the SIOT auth token with full access for every client kind
  (existing NATS clients must keep working — custom auth replaces auth on all
  listeners), and accepts MQTT clients matching an `mqttUser` with
  `RegisterUser` permissions scoped to their topic prefix, so a gateway can
  publish only its own site's subjects and revocation is deleting one node.
  Verify scoped permissions do not disturb `$MQTT_*` session persistence.
- Schema-less topic discovery (browsing what an unfamiliar broker publishes
  under a prefix, Shelly-style). The topic schema in Phase 4 covers the
  structured case; this covers exploration when no convention exists.
- Offline marking for schema-created nodes that stop publishing (a quiet sensor
  and a removed sensor look the same from outside; needs a timeout setting).
- Sparkplug primary-host STATE participation and publishing Simple IoT data
  outbound as Sparkplug.
- Payload timestamp extraction for plain JSON payloads.

## Test Plan

### Shared infrastructure (Phase 1)

- Add `NatsMQTTPort` to `server.TestServerOptions` (8904) and
  `TestServerOptions2` (8914) so every client test can reach the broker without
  private setup.
- `internal/mqtttest`: a minimal MQTT 3.1.1 test client speaking only the
  packets the tests need (CONNECT/CONNACK, PUBLISH/PUBACK, SUBSCRIBE/SUBACK,
  PINGREQ, DISCONNECT). Hand-rolled rather than importing `paho.mqtt.golang`,
  keeping go.mod clean; the packet set is small and doubles as a check that the
  broker speaks the wire format, not just that two libraries agree with each
  other. Revisit when external-broker support brings a client library in anyway.
- Restart tests use `server.TestServerOptsKeepStore` to bring the instance back
  on the same store.

### Phase 1 — broker (`server/mqtt_test.go`)

Unit (conversion helpers, table-driven, both directions):

- `a/b/c` ↔ `a.b.c`; literal `.` ↔ `//`; the documented
  `spBv1.0/plant/DDATA/line3/tank` ↔ `spBv1//0.plant.DDATA.line3.tank`;
  wildcards `+` → `*`, `#` → `>`.

Integration:

- **Off by default:** port unset → nothing listening on the MQTT port.
- **MQTT → NATS:** CONNECT/PUBLISH; message arrives on the converted subject
  with the payload intact.
- **NATS → MQTT:** subject publish reaches an MQTT subscriber (the direction
  rebirth requests depend on).
- **Auth:** token-configured server refuses a CONNECT with a missing or wrong
  password (CONNACK return code, not a hang) and accepts the token in the
  password field; a server without a token accepts anonymous.
- **QoS 1:** PUBLISH is acknowledged with PUBACK and delivered.
- **Persistence:** publish a retained message, restart via
  `TestServerOptsKeepStore`, a fresh subscriber receives it — this also
  exercises `ServerName` stability, since sessions are keyed by it.
- **Store isolation:** after MQTT use, the `$MQTT_*` JetStream streams are
  ignored by SIOT stream enumeration (store/sync assertions pinned down during
  implementation).

### Phase 2 — subscription client (`client/mqtt_test.go`)

Unit:

- Dot-path extractor table: `$.value`, nested `$.a.b`, array index `$.a[0]`,
  missing path (no point published, error point set), type mismatch, blank path
  against scalar / string / object payloads.
- Payload → points mapping: scale/offset on numeric values, text points for
  strings, object fields become point keys.

Integration (over the built-in broker via `mqtttest`):

- Publish → `value` point on the `mqttSub` node, timestamped at arrival.
- Object payload → one point per field with the field name as key.
- Editing `topic` resubscribes; `disabled` stops point flow; re-enable resumes.
- Non-blank `uri` → error point on the node, client keeps running.
- Two blank-`uri` `mqtt` nodes coexist and each receives only its topics (the
  multi-site shape).
- `tag:topic` point present on the `mqttSub` node.

### Phase 3 — Sparkplug (`client/sparkplug_test.go`)

Unit:

- Topic parser table: NBIRTH/NDATA/NDEATH (no device level),
  DBIRTH/DDATA/DDEATH, STATE, malformed topics rejected.
- Protobuf decode against a golden payload fixture generated from the vendored
  proto.
- Metric name sanitization (`Node Control/Rebirth` and friends through
  `SubjectSafeToken`); Sparkplug → point type mapping (BOOL→int, numeric,
  String→text).
- Alias cache: resolve, miss, rebuild from a second birth.

Integration:

- NBIRTH + DBIRTH → group/edge/device nodes created, one point per metric with
  birth values.
- DDATA by alias → point update carrying the payload timestamp.
- **Rebirth:** restart the instance (`TestServerOptsKeepStore`) so the alias
  cache is lost, publish DDATA with an unresolvable alias → NCMD
  `Node Control/Rebirth` observed on the converted subject; replayed NBIRTH
  rebuilds the cache and creates no duplicate nodes.
- NDEATH/DDEATH → node marked offline (`sysState`); a later birth marks it
  online again.
- A user-added tag point on a `sparkplugDevice` survives a rebirth refresh.

### Phase 4 — topic schema (`client/mqtt_schema_test.go`)

Unit:

- Schema parser: `{site}/{device}`, fixed prefix `plant/{site}/{device}`,
  invalid schemas (empty label, duplicate labels, label after remainder),
  derived subscription string.
- Point key construction: exact-depth topic with scalar payload, deeper topic
  joining remaining levels, object payload appending field names, sanitization
  of level values.

Integration:

- First message → auto-created node path with tag and identity points.
- Second message on the same topic → points update, no new nodes.
- Restart on the kept store, then publish → nodes matched by identity point; a
  user-renamed description and added tag survive.
- `maxNodes` reached → error point on the `mqtt` node, new topics dropped,
  existing nodes keep updating.
- Precedence: a topic named by an explicit `mqttSub` produces exactly one point
  stream (the sub's, with its units/scale) and no schema-created nodes.

### Frontend

New components follow the existing pattern: `elm-review` clean, `elm-test` for
any logic beyond form plumbing (none expected initially).

Each phase: `siot_test` (backend `go test -race ./...`, frontend
`elm-review`/`elm-test`, `golangci-lint run`), plus a manual check with
`mosquitto_pub`/`mosquitto_sub` against a running instance. Commit at the end of

## Implementation notes

What shipped differs from the plan above in a few places, each for a reason
worth recording.

**The topic conversion helpers live in `data/mqtt.go`.** The plan put their
tests in `server/mqtt_test.go`, but the subscription client needs the same
conversion, so they sit in `data` where both the server and the client reach
them, with table-driven tests in `data/mqtt_test.go`.

**The NATS server name comes from the instance ID or the store directory.** The
plan called for the root node ID, which lives in a JetStream KV and so is not
readable until after the NATS server has started. `Options.ID` is used when it
is set, and otherwise a digest of the absolute store directory, which identifies
the instance just as well and is available at start-up.

**Subscriptions require the `Nmqtt-Pub` header.** MQTT messages reach the client
as ordinary NATS subjects, and a schema of `{site}/{device}` converts to a
subject of `*.*`, which also matches Simple IoT's own point traffic and the NATS
server's internal subjects. The embedded broker puts `Nmqtt-Pub` on every
message that arrived over MQTT, so requiring it keeps a wildcard subscription to
what MQTT clients actually published.

**A filter ending in `#` needs two NATS subscriptions.** The MQTT remainder
wildcard matches the level above it -- `plant/#` matches `plant` -- while the
NATS `>` it converts to needs at least one token. Both subjects are subscribed,
which is what makes a topic schema match a topic of exactly its own depth.

**The Sparkplug alias assignment is persisted on the `sparkplugNode` node.**
Creating a node restarts the client that created it, so an in-memory cache would
be lost on the message right after a birth certificate, and the rebirth that
followed would create nodes and restart the client again. Writing the assignment
as a JSON point means a restart resolves aliases straight away. A rebirth is
still requested, rate limited per edge node, when an alias has no mapping at all
-- data from a gateway that was already running when Simple IoT started. The
Phase 3 test covers that case rather than the restart case the plan described,
since a restart no longer loses the cache.

**Schema point keys join with `/`.** The plan left the separator open. `/` keeps
the shape of the topic the key came from and is legal in a point key, where `.`
is not.

**Sparkplug metrics carrying a dataset, template, or file are skipped**, with
the rest of the message used. Those types have no point representation yet.
